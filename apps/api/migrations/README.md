# Migrations

Generated by `vp run @family-hub/api#db:generate` from `src/common/db/schema.ts`, reviewed like code, applied to production by the deploy workflow with `wrangler d1 migrations apply --remote` **before** the new Worker goes live. Never edit a migration that has reached `main`; write a new one.

## Expand / contract

Between the migration step and the Worker deploy — and for as long as a failed deploy keeps the previous Worker live — the **old** Worker runs against the **new** schema. Every migration must therefore be safe for the code currently in production.

1. **Expand** — add only: new tables, new nullable columns or columns with a default, new indexes. The old Worker ignores them. Ship the code that writes and reads them in the same or a later release.
2. **Migrate data** — backfill in a migration or from the Worker once the new code is live. Mind the D1 budget of 100k written rows a day, indexes included.
3. **Contract** — drop or rename only in a **later** release, once no deployed Worker reads the old shape. A rename is add → copy → switch the code → drop, across at least two merges.

Not allowed in one release: dropping or renaming a column or table the live Worker uses, adding `NOT NULL` without a default, tightening a constraint the live Worker may violate.

Rollback is manual (`wrangler rollback` for the Worker; D1 Time Travel keeps 7 days), and an expand-only migration never needs to be undone for the previous Worker to work.
